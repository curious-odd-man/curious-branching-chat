# Security review (phase 9)

Reviewed against ADR-001 section 7 and requirements NFR-005 to NFR-010, NFR-016 and acceptance criterion 23. The
automated evidence is `tests/e2e/security.spec.ts` and the unit tests in `tests/validation` and `tests/document`.

## Threat model

The main risk is a `.branchchat` file received from someone else (WhatsApp, e-mail): it is untrusted input. The
application has no server and no accounts. Secondary risks: the update channel, and links or images inside messages.

| Area               | Control                                                                                                                                                                                                                                                                                   | Evidence                                                                                                                                                                                                     |
|--------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

## Accepted risks

- **Unsigned installer (decision, NFR-016).** Windows SmartScreen warns on first download. Mitigation: documented steps
  in the user guide and release notes, SHA-256 in every release, CI-only builds. A later release may add signing
  (see implementation plan section 10).
- **Read status is visible to others** by design (FR-125); the person is told once.
- **A file from an untrusted person can be very large.** No limit is enforced by decision (NFR-015); a huge file only
  slows the application, it cannot execute code.
- **Spell check** uses the Windows spell checker; words are not sent anywhere by BranchChat.

## Release 2.4: file attachments (phase 14)

Attachments are a new attack surface: a member of a shared discussion, or the author of a received file, can send any
file. Review of 2026-11-16:

| Area                   | Control                                                                                                                                                                                                                                                                                                                                                                                                            | Evidence                                                      |
|------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------|
| Opening                | Never automatic (FR-264): only after a click on "Открыть". The app copies the file to a new folder (random name) in `%TEMP%\BranchChat\open` and lets Windows open the copy (`shell.openPath`); the stored bytes are never opened. Copies older than 7 days are removed at start                                                                                                                                   | `attachments.test.ts`, `release24.spec.ts`                    |
| Warned types           | `.exe`, `.bat`, `.cmd`, `.ps1`, `.js`, `.vbs`, `.msi`, `.lnk`, `.docm`, `.xlsm`: a warning with the type and the author before "Открыть" (FR-267); nothing is blocked. The type comes from the name of that message, which is also the name of the opened copy, so Windows chooses the program by the warned type                                                                                                  | `release24.spec.ts` (`.bat`), `attachments.test.ts` (`.ps1`)  |
| Mark of the Web        | Saved and opened copies get `Zone.Identifier` with `ZoneId=3` (FR-263): SmartScreen, Office Protected View, and macro blocking apply. A drive without NTFS streams (FAT32) cannot keep the mark: accepted                                                                                                                                                                                                          | checklist T4, T5                                              |
| Names and paths        | The renderer names an attachment only by message and position; name and hash come from the discussion. Names in files and events are refused with control or direction characters (also U+202E), path separators, `: * ? " < > \|`, a space at the start or end, a dot at the end, more than 200 characters. Names of new files are made safe (replaced characters, `_con.txt`, the extension kept when shortened) | `release24.test.ts` (sync and library), `attachments.test.ts` |
| Same hash, other names | The bytes are stored once (FR-266); each message keeps its own name, and the warning and the copy use that name                                                                                                                                                                                                                                                                                                    | design                                                        |
| Integrity              | Import: size and SHA-256 of `attachments/<sha256>` must match, else the file shows as missing. Sync: each part is checked against the signed list of its author; the joined file must match size and hash; only the author of a message can attach files to it, once                                                                                                                                               | `release24.test.ts`                                           |
| Size                   | "Наибольший размер вложения" (default 100 MB) for own files; the receiver's file size limit for files of others (they wait in the shared folder until the limit is raised, FR-268a). Files are copied as streams, not read into memory, when they are attached, saved, or opened                                                                                                                                   | `attachments.test.ts`, `shared.spec.ts`                       |

Accepted: a dropped or pasted file is read from the path that the window gives (Electron `webUtils.getPathForFile`).
A changed renderer could name another local file of the person, but the renderer is sandboxed, loads no remote
content, and the file would be visible in the draft before it is sent.

## Not covered

Penetration testing by a third party; dynamic analysis of Chromium itself (kept current by upgrading Electron).
